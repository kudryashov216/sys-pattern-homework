### Задание 1

1. Активный master и пассивный slave
Это классическая схема репликации «один в один»: есть основной сервер (master), который принимает все записи и изменения, и один резервный (slave), который только читает данные и постоянно синхронизируется с мастером.

Основные преимущества:

- Отказоустойчивость (Failover). Если master падает, slave можно быстро перевести в режим мастера. Это минимизирует простой системы;

- Разгрузка на чтение. Все тяжёлые SELECT-запросы, отчёты и аналитика уходят на slave. Master остаётся свободным для операций записи (INSERT, UPDATE, DELETE), что повышает общую производительность;

- Безопасность данных. Slave-сервер выступает в роли «горячего» бэкапа. Данные уже находятся на другой машине, их не нужно восстанавливать из дампа;

- Тестирование и проверка. На slave можно запускать тяжёлые проверки целостности, эксперименты с новыми версиями СУБД или миграциями, не рискуя основной базой;

2. Master + несколько slave-серверов
Здесь архитектура расширяется: один мастер и множество реплик.

Дополнительные преимущества по сравнению с одним slave:

- Масштабирование чтения (Read Scaling). Можно распределить нагрузку от тысяч пользователей по нескольким slave-серверам. Если трафик вырастет в 5 раз, достаточно добавить ещё пару реплик;

- Географическое распределение. Slave-серверы можно разместить в разных дата-центрах или регионах. Пользователи из Европы будут читать данные с европейского slave, а из Азии — с азиатского. Это сильно сокращает задержку (latency);

- Изоляция задач. Разные slave-серверы могут выполнять разные роли: один — для веб-приложения (быстрые запросы), второй — для тяжёлой аналитики, третий — для резервного копирования. Они не мешают друг другу;

- Постепенный вывод из эксплуатации. Если нужно обновить оборудование или версию СУБД, можно выводить slave-серверы из работы по одному, не влияя на общую доступность сервиса.

### Задание 2

Шаг 1: Вертикальный шардинг (по таблицам)

Разнесём таблицы по разным логическим базам данных (или разным физическим серверам), чтобы изолировать нагрузку.

- users → База данных DB_USERS. Эта таблица критична для авторизации и профиля. Она должна быть максимально быстрой для точечных 
запросов (поиск по ID, поиск по email);

- books → База данных DB_BOOKS. Это самая большая таблица по объёму данных и количеству запросов. Здесь будет применяться горизонтальный шардинг;

- stores → База данных DB_STORES. Справочная информация. Обычно небольшая, но часто читается вместе с книгами (чтобы показать, где есть товар).

Шаг 2: Горизонтальный шардинг для таблицы books

Таблица books будет разбита на несколько шардов (например, 4 шарда). Ключ шардирования — id книги.

Стратегия: Hash-based. Вычисляем hash(book_id) % 4. Результат (0, 1, 2, 3) указывает, на каком шарде искать книгу.

Распределение:
Шард 1 (DB_BOOKS_SHARD_1) — книги с хешем 0.
Шард 2 (DB_BOOKS_SHARD_2) — книги с хешем 1.
Шард 3 (DB_BOOKS_SHARD_3) — книги с хешем 2.
Шард 4 (DB_BOOKS_SHARD_4) — книги с хешем 3.

Шаг 3: Репликация внутри шардов

Каждый шард книг имеет свой Master (для записи новых книг/обновления остатков) и 1–2 Slave (для чтения каталога пользователями).
